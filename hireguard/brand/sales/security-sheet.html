Security and data-protection overview

What we enforce, what we measured, and what is not done yet.

For your IT and security reviewer. Every row names how it was checked. Nothing here has been tested by an outside party yet: it is our own code review, internal penetration test and automated tests (about 540 backend and 17 frontend).

The design in one paragraph

The model that reads untrusted text is quarantined: it has no tools, no memory between documents, and returns only typed fields (skills, dates, degree, languages). Code then checks every field against the visible text, a deterministic scorer ranks the candidates, a person approves every consequential action, and the executor refuses anything not approved. A fully manipulated model output can only choose values inside that schema, and each value must survive the check and a human. The model is not the security boundary; the checks and the approval step are.

Your data

  • The model runs on your own servers. A cloud model is off by default and is blocked in production unless you acknowledge it
  • Identity details (town, school, gendered titles, emails) are masked before the model reads a CV
  • Team views are aggregates, never per person; the question radar hides groups under 5 (the skills map shows holder counts, and small-team handling is still to be decided)
  • No performance, productivity or stress scoring of employees

What we measured

  • Hidden-text attacks changed a result 3 of 40 times (naive screener 13 of 40)
  • Plain-sight manipulation changed a result 7 of 14 times (naive screener 8 of 14): human review is the answer
  • Same-CV-different-town/school/gender changed no score; changing only the CV's language changed 13 of 20
  • All on synthetic CVs, attacks written by our team
